# App Store Connect 多语种文案

把一份源文案（通常是简体中文，也可能是英语等其他语言）做成 App Store Connect（下称 ASC）39 个语种的「推广文本」和「此版本的新增内容」，写进一个本地 Markdown 文件，供用户逐个语种复制到 ASC。

开始前读两个参考文件：

- `references/format.md`：字段上限与计数方法、新增内容格式、内容取舍、长度预算与压缩、简体中文写法、推广文本写法、输出文件结构。它与 `app-store-connect-copywriting` 中的同名文件完全相同。
- `references/locales.md`：39 个语种各自的小节标题，以及引号、称呼、拼写和地区差异等要点。

两个字段的上限（推广文本 170、新增内容 4000）是硬性条件，每个语种都要用 `scripts/asc_check.py` 实测，不能凭感觉判断。下文 `<skill>` 指本文件所在目录。

## 工作流程

### 1. 弄清输入

- **app-store-connect-copywriting 产出的文件**（`asc-<app>-<版本号>-zh-Hans.md`，或任何带「## 简体中文」「### 推广文本」「### 此版本的新增内容」的文件），或同一对话里刚生成的中文文案：其中的简体中文已按同一份规范写好并校验过，直接作为母版。只需按 format.md 第 4 节确认在预算内；措辞不要再改，除非为了预算必须压缩（汇报时说明）。App 名和版本号沿用该文件的元信息。
- **还没有文案，只给了版本号、分支、diff 等变更**：先用 app-store-connect-copywriting 写出简体中文文案，请用户确认后再翻译。39 个语种的工作量很大，母版有问题就得全部返工。没有那个 skill 时，请用户提供文案。
- **有哪几项**：只翻译用户给出的项。没标明时按内容判断：一两句宣传语是推广文本，分条列出的改动是新增内容；判断不了再问。用户要推广文本却没给原文时，可以从新增内容的亮点提炼一句源语言草稿，先请用户确认再翻译——这是对外的营销文案，应由用户拍板。
- **源语言**：通常是简体中文；是英语或其他语言时流程相同，母版换成那种语言即可。
- **源文本的形式**：可能是纯文本，也可能是 Markdown 文件（带 `---` front matter、`###` 标题、`-` 列表）。一律只取内容，按 format.md 重新排版；front matter 里如果有一句话的摘要，可以作为摘要行；版本号、日期、标题不进 ASC 文案（ASC 自己会显示版本号和日期）。
- **现成译文**：用户提供了某些语种的现成译文或参考文件（App 的本地化字符串、以前版本的商店文案等）时，以它为对应语种的基础并沿用其中的术语，再按规范的格式和长度整理。
- **App 界面支持哪些语言**：只在文案引用了界面文字时才需要知道（见 format.md 第 3 节）。用户说明了就照办；当前目录正好是这个 App 的工程时，可以看本地化文件（如 `.xcstrings`、`*.lproj`）；都没有就问用户一次。
- **文件名所需信息**：App 名和版本号，从用户的话、源文件或源文本里取；没有就用日期。

### 2. 定稿母版

先把源文本整理成符合 format.md 的「母版」，再从母版翻译出所有语种。所有语种的内容、小节、条目数和顺序都与母版一致——不能德语少一条、日语多一条，否则不同地区的用户看到的更新内容就不一样了。

- 新增内容按 format.md 第 2、3 节整理：零散条目归入对应小节、改写成完整的句子；母版语言的写法按第 5 节（简体中文）或 `references/locales.md` 中该语种的要点。
- 推广文本按第 6 节修整。
- 两项都按第 4 节的预算控制，用 `python3 <skill>/scripts/asc_check.py count <文本文件>` 实测；超出时按第 4 节的顺序压缩母版，再同步到所有语种。

### 3. 逐语种翻译

- 按「语种顺序」一节依次翻译 39 个语种。先做英语（美国）并用 `count` 测一下：新增内容超过 2800 就回到第 2 步继续压缩母版，再往下做。
- 每个语种按 `references/locales.md` 中的小节标题与要点（句式、引号、称呼、拼写、地区差异）来写。
- 译文要地道，读起来像该语种的母语者为 App Store 写的，而不是从源语言直译过来的：
  - 先理解每条改动对用户意味着什么，再用目标语言的自然说法表达；不保留源语言的句式、语序和四字词。
  - 语气克制、清楚、以用户为中心，像 Apple 自己的更新说明：主动语态，少用感叹号和空泛的形容词。
  - 术语在同一语种内统一，跨版本也尽量不变。
- 界面文字和 Apple 系统名词按 format.md 第 3 节处理：App 界面不支持该语种时，不要自行翻译菜单名。
- 推广文本按第 6 节为每个语种重新创作，而不是逐字翻译。
- 地区变体（英语四个、法语两个、葡萄牙语两个、西班牙语两个）不要不加检查地互相复制：逐条核对拼写、用词和标点习惯，确实没有差异的地方可以相同。

### 4. 写入 Markdown 文件

- 位置与结构按 format.md 第 7 节。文件名 `asc-<app>-<版本号>.md`（如 `asc-photo-viewer-2.1.0.md`，App 名小写、空格换成短横线）；没有版本号用 `asc-<app>-<YYYY-MM-DD>.md`；App 名也不知道就用 `asc-localization-<YYYY-MM-DD>.md`。
- 一级标题写「App Store Connect 多语种文案」，元信息里写明源语言；母版来自某个文件时，也写上源文件名。
- 语种按「语种顺序」排列，每个语种下推广文本在前、新增内容在后。

**分批写入**：39 个语种的全文很长，一次写不完。每批写 5–8 个语种（新增内容较长时取下限）：第一批用写文件工具创建文件（含一级标题和元信息），之后每批追加到文件末尾，例如：

```bash
cat >> "<输出文件>" <<'ASC_EOF'
## 波兰语
…
ASC_EOF
```

分界符带引号（`'ASC_EOF'`），shell 就不会改动文案里的 `$`、反引号等字符。

### 5. 校验并修正

```bash
python3 <skill>/scripts/asc_check.py check "<输出文件>"
```

脚本会检查：

- 语种名称、顺序与完整性（39 个，缺一个就报错；用户只要部分语种时加 `--allow-subset`）；
- 每个语种里推广文本在前、新增内容在后，且都恰好有一个非空代码块；
- 字符上限；
- 新增内容的小节标题是否与该语种的标题表一致、顺序是否正确，列表项是否以 `• ` 开头；
- 各语种的小节与条目数是否一致。

有错误就修正对应语种（超限时改写得更紧凑，不要直接截断句子），再重新运行，直到输出「结果：通过」。警告（非 NFC、行尾空白）也顺手处理。没有通过校验的文件不交给用户。

### 6. 汇报

在对话里简短说明：

- 文件路径（母版来自某个文件时，也提一下源文件）；
- 校验结果，以及每个字段最长的语种和字数（脚本输出的最后几行）；
- 需要用户知道的决定，例如母版做了哪些压缩、界面文字怎么处理的。

不要把 39 个语种的全文贴进对话，用户去文件里看。
