# App Store Connect 文案撰写（简体中文）

根据一段代码变更，写出可以直接粘贴到 App Store Connect（下称 ASC）的简体中文「推广文本」和「此版本的新增内容」，写进本地 Markdown 文件，并在对话里展示。

格式、内容取舍、长度预算、简体中文写法和输出文件结构都在 `references/format.md`，开始前先读。它与 `app-store-connect-localization` 中的同名文件完全相同，所以这里的产出可以直接交给那个 skill 翻译成 39 个语种。下文 `<skill>` 指本文件所在目录。

## 工作流程

### 1. 确定变更范围

| 用户给的 | 怎么确定范围 |
| --- | --- |
| 版本号，已打 tag（如 `v3.1.0`、`3.1.0`） | 上一个发布 tag 到该 tag；上一个 tag 用 `git describe --tags --abbrev=0 <tag>^` 查 |
| 版本号，尚未打 tag | 最近的发布 tag 到该版本的开发分支（如 `release/3.1.0`、`feature/3.1.0`），找不到就用当前分支 |
| 分支 | 主分支与它的分叉点到分支末端（`git merge-base <主分支> <分支>`）；主分支用 `git symbolic-ref --short refs/remotes/origin/HEAD` 查，查不到就试 main、master |
| tag 或提交范围（`a..b`） | 直接使用 |
| diff 文件或贴进对话的 diff | 就是全部变更 |
| "当前的改动" | `git diff HEAD`，加上未跟踪的新文件 |
| PR 编号或链接 | `gh pr view <编号> --json title,body,commits` 与 `gh pr diff <编号>` |
| 一段改动记录（issue 列表、笔记等） | 直接作为素材 |

新增内容写的是相对"用户上一次拿到的版本"的变化，所以基线是上一个已发布版本，而不是某个中间提交。推断出的范围要在汇报里写明；实在推断不出（仓库没有 tag、分不清哪个是上一个发布版本等）时再问用户。

同时确定 App 名和版本号（用于文件名和元信息）：从用户的话、tag、工程配置（如 `MARKETING_VERSION`、`Info.plist`、`package.json`）里取。

### 2. 收集改动

按信息密度从高到低看，够用就停：

1. **仓库里的 CHANGELOG 或发布说明**：如果有对应版本的小节，它通常已经是整理过的用户视角改动，以它为主要依据，再用提交核对、补漏。注意其中可能夹带模块名等内部信息，写文案时按 format.md 第 3 节去掉。
2. **提交记录**：`git log --no-merges --format='%h %s%n%b' <范围>`。
3. **改动概览**：`git diff --stat <范围>`，找出与用户相关的文件。
4. **关键 diff**：本地化字符串文件（`.xcstrings`、`.strings`、`.po` 等）的改动最有用，它直接列出用户能看到的新文案和改动过的文案，也是引用界面文字时照抄的来源；其次是界面、菜单、设置、付费限制、文件格式支持等代码。

提交说明可能不准或过于简略。拿不准某个提交对用户意味着什么时，去读它的 diff。范围很大（上百个提交、数万行 diff）时不要通读全部 diff，以提交记录和本地化字符串为主线，只深入读重要或含糊的部分。

### 3. 筛选与归类

- 按 format.md 第 3 节只保留用户能感知的变化。
- 开发过程中引入、又在同一范围内修掉的问题不写：用户在上一个版本里从没遇到过它。判断方法是看被修的功能或代码是否也在本范围内新加——是的话，这个修复只是新功能的一部分。看不出来时，用 `git log -S'<出问题的关键代码>' --oneline -- <文件>` 找到引入它的提交，再用 `git merge-base --is-ancestor <该提交> <基线 tag>` 判断：成立说明上个版本就有这个问题，要写进修复。
- CHANGELOG 没记、但提交里有的用户可见改动（尤其是老问题的修复）要补上；CHANGELOG 里记了、实际上属于上一条情况的，不写。
- 同一功能分散在多个提交里的，合成一条；一个提交里包含几项用户可见变化的，拆开放到各自小节。
- 按 format.md 第 2 节的表归入 新增 / 优化 / 修复 / 性能 / 安全 / 移除。
- 付费功能：代码或说明里能确认需要付费解锁时才标注。
- 读完仍不确定的改动（看不出用户能否感知，或作用不明），不要猜着写进文案，在汇报里单独列出，请用户决定。

示例：某个范围里有这些提交——

```text
a1b2c3d feat(format): 支持 AVIF / JPEG XL / HEIF 浏览
d4e5f6a fix(format): 打开损坏的 .jxl 文件时崩溃
b7c8d9e refactor: 抽出 FormatUtils
e0f1a2b ci: 新增本地化检查
c3d4e5f feat(l10n): 新增日语界面
f6a7b8c fix(about): 英文界面下评价提示被截断成一行
```

`d4e5f6a` 修的是本范围新加的 .jxl 支持，用户没遇到过这个崩溃，不写；`b7c8d9e`、`e0f1a2b` 是内部改动，不写；其余三条进入新增（两条）和修复（一条），写出来就是 format.md 第 8 节简体中文示例的样子。

### 4. 撰写

- 先写「此版本的新增内容」，按 format.md 第 2、5 节；再从中提炼「推广文本」，按第 6 节。用户只要其中一项时，只写那一项。
- 长度按第 4 节的简体中文预算：新增内容约 900 字以内、推广文本约 60 字以内，这样之后翻译成 39 个语种也不会超限。超出时按第 4 节的顺序压缩。用户明确说只用中文、不做翻译时，新增内容可以放宽，但不能超过 4000。

### 5. 写入文件并校验

- 位置按 format.md 第 7 节。文件名 `asc-<app>-<版本号>-zh-Hans.md`（如 `asc-photo-viewer-2.1.0-zh-Hans.md`，App 名小写、空格换成短横线）；没有版本号时用分支名或日期代替。
- 一级标题写「App Store Connect 文案」，文件里只有「简体中文」一个语种。元信息里加一行「变更来源」，写明范围和提交数（如 `v2.8.0..feature/3.0.0，42 个提交`）。
- 校验：

  ```bash
  python3 <skill>/scripts/asc_check.py check "<文件>" --allow-subset
  ```

  脚本检查字符上限、小节标题与顺序、列表项格式等。有错误就修正后重新运行，直到输出「结果：通过」。

### 6. 汇报

- 把文案贴到对话里（中文篇幅不长，用户可以直接审阅、复制），格式与文件中的「简体中文」部分一致：每段文案上方用标题注明是哪一项，文案本身放进 ```` ```text ```` 代码块，推广文本在前。不要只贴两个没有标题的代码块，否则用户分不清该粘贴到 ASC 的哪个字段。

  ````markdown
  ### 推广文本

  ```text
  （推广文本）
  ```

  ### 此版本的新增内容

  ```text
  （此版本的新增内容）
  ```
  ````

  用户只要其中一项时，只贴那一项，标题照样保留。
- 文件路径、使用的变更范围、两项的字数；
- 没写进文案的改动里值得用户留意的（比如拿不准的条目），以及做过的压缩；
- 最后提一句：需要多语种版本时，可以让 app-store-connect-localization 直接翻译这个文件。
